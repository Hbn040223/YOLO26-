# MobileNetV2 0.5× 编码器替换实施计划

> 实施时按任务逐项完成测试、代码和服务器验证。本文定义本轮的设计和验收口径。

**目标**　把 0.5× 接成 `加速` 分支的可选编码器，先验证服务器的权重迁移、精度和速度，再用相同模型在 Jetson Orin NX 验证端到端吞吐。

**设计**　缩窄 MobileNetV2 主干并重建配套的 LightStereo FPN 和适配层。保持左右目共享一次编码调用，保留四个空间尺度和四个 96 通道输出。用现有检测、Car Mask 和 iDisp 权重初始化下游，适配新特征后再判断能否推广到部署配置。

**技术栈**　项目现用 PyTorch、OpenStereo `23d71c9`、`timm 0.4.12`、KITTI2015。加速组沿用 AMP 与 ONNX/TensorRT 前端，具体后端按板端实测选择。

**基线**　[GitHub 加速分支的 9010f95](https://github.com/Hbn040223/YOLO26-/commit/9010f95339727d7215dc5ce9254eef7b25057311)。在这个提交的同树服务器版本上，GPU 2 的 120 秒原生 5 Hz 回放完成 600/600，P95 47.31 ms，不限速为 32.33 对/秒。相同 40 帧上，当前 R2 处理了 51 对 RoI，10 米内 Car 为 18/23 命中，零对／一对／多对为 5／17／1，precision 为 18/26。 [服务器回放](../../../outputs/gpu2-review-2026-11-25/r2-fp32-5hz.json) · [近距精度](../../../outputs/gpu2-review-2026-11-25/accuracy-fp32.json)

## 全局实验口径

- 第一轮只改变编码器版本及其适配训练。保持全图输入、双目 batch 1、输入归一化、检测分类映射、`legacy_clamp` 右框偏移、one-to-one 配置、score 0.40、pre-NMS top-K 500、同类 paired NMS IoU 0.50。
- 保持 `fixed_56`、RoI margin 16、`dmax_roi=16` 的 33 个视差档。近距策略沿用 `range-dedup`、15 米框粗筛、10 米精测输出、双目 IoU 0.45 的 Mask 复核开关及 Mask IoU 0.50。
- 40 帧开发集使用 `pilot_random_seed17/val.json` 和原标定压缩包。开发集用来调试和同帧对照。部署结论另用独立近距样本复核，按训练清单和来源序列检查重叠。没有独立样本的类别继续记录为待验证。
- 本地结构原型在 375×1242 双目输入上跑通。1.0× 的适配前通道为 `[24,32,96,160]`，0.5× 为 `[16,16,48,80]`。卷积计算量含 FPN 和适配层，从 7.56 降到 2.47 GMAC，约少 67%。这是结构算量，板端毫秒数由同机实测给出。

## 需要优先验证的边界

| 输入或状态 | 验证方法 |
| --- | --- |
| 奇数尺寸及左右视图顺序 | 任务 1 用三种真实分辨率和不同左右输入验证共享调用及各尺度形状 |
| 旧包缺编码器字段，或新包标签与权重矛盾 | 任务 2 验证默认 1.0× 和新版严格加载 |
| 前景包采用 `context` Mask 头及已有阈值校准 | 任务 2 验证模块类型与单次校准；任务 3 做实际 Mask 覆盖复测 |
| 40 帧没有可确认近距的非 Car GT | 任务 4 按类出分母，分母为零的 recall 记 `N/A` |
| 同名引擎的尺寸、权重 SHA 或编码器版本不一致 | 任务 5 验证运行时在推理前拒绝不匹配的 manifest |

## 任务 1　接入 0.5× 并测编码器负载

**测试与实现**　`tests/test_lightstereo_encoder.py`、`src/lightbackbone_stereo_yolo/lightstereo_encoder.py`、`scripts/benchmark_edge_backbone.py`。

- [ ] 给 `build_lightstereo_backbone(source_root, *, encoder_backbone="v2")` 增加测试。取值为 `v2` 或 `v2-050`。0.5× 的 `output_channels` 是 `(16,16,48,80)`。对 `375×1242`、`376×1241`、`374×1238`，输出每目四层，每层 96 通道，空间尺寸分别按步长 4、8、16、32 向上取整。不同左右输入的结果要与同一编码器逐目执行的结果对齐。四尺度接口沿用当前 `StereoFeaturePyramid`。
- [ ] 就地复用固定版 TIMM 的 V2 构造器，传入 `channel_multiplier=0.5`，构造特征主干时禁止自动下载。保留当前 stem 与分段层索引。从实际输出层读取通道数，据此构建 LightStereo FPN、P2 输出层和 96 通道适配层。`(16,16,48,80)` 是固定版本的测试预期。原 `v2` 入口保留现有构造和参数名。固定版 TIMM 的模型注册表只提供项目现用的 V2 1.0× 等变体，开发时增加项目内选择器。 [固定版 TIMM 构造源码](https://github.com/huggingface/pytorch-image-models/blob/v0.4.12/timm/models/efficientnet.py)
- [ ] 在现有骨干 benchmark 上添加候选 `--candidate-backbone v2-050`，同帧交替执行 V2 两种宽度。报告编码器 P50/P95、显存和固定 0／1／3／6 对 RoI 的前向。固定 1、3、6 对覆盖当前线上负载中位数、P95 和最大值。结构原型的对照报告标明初始化来源，精度使用任务 3 的训练权重复测。

## 任务 2　解决 checkpoint 迁移与回读

**测试与实现**　`tests/test_training_checkpoint.py`、`tests/test_lightstereo_encoder.py`、`scripts/train.py`、`scripts/infer.py`。

- [ ] 新 checkpoint 在 `config.encoder_backbone` 存 `v2-050` 或 `v2`。旧包缺该字段时按 `v2` 构建。训练入口增加 `--encoder-backbone v2-050`，恢复时读已存配置，显式指定不同版本则报错。两个版本都用整模型严格载入进行推理。报告记录实际结构、各尺度通道、初始化文件 SHA、训练数据 SHA 和提交。
- [ ] 加独立的 `--encoder-init` 路径加载 0.5× 主干预训练权重。先用官方或可追溯来源核对 stem、各 block 张量名及形状，再载入主干。为新通道的 FPN 与 96 通道适配层做新初始化。旧版 fresh run 沿用 `--checkpoint` 载入 LightStereo 权重。半宽 fresh run 使用 `--encoder-init`，resume 直接从完整训练包恢复。若兼容预训练权重尚未确认，结构测试及一次训练 preflight 可显式使用随机 0.5× 初始化并记录来源，正式训练另记录最终采用的初始化。
- [ ] 使用 `--init-weights models/foreground_evaluation.pt` 迁移下游。半宽迁移只复制语义相同、形状一致的 `detector.*`、`instance_head.mask.*` 和 `instance_head.idisp.*`。类映射、one-to-one、`right_offset_mode`、`fixed_56` 或 `dmax_roi` 不一致时明确拒绝。迁移后列出已加载和新初始化的模块，随后完整保存新的 student checkpoint。
- [ ] 将训练入口的 Mask 结构设为可记录配置。以 Car 前景包 warm-start 时，用它的 `context` Mask 结构，训练后随权重记录真正适用的 Car 支持元数据和 Mask 阈值。对已折入 logit 偏置的阈值沿用 `resolve_mask_threshold()` 的语义，导出时核对只校准一次。普通 E20 的 `light` Mask 及原有初始化路径继续能运行。
- [ ] 添加回归用例覆盖旧包默认、半宽包回读、未知版本、跨版本续训、误用 1.0× 主干权重和漏载 `context` Mask。跑编码器和 checkpoint 相关用例，再跑仓库测试套件。

## 任务 3　服务器预检与正式训练

**入口**　`scripts/train.py` 的 `--preflight`、`--init-weights`、近距检测及 Pred-RoI 验证；沿用现有训练数据、损失和优化器分组。

- [ ] 对 0.5×、Car 前景包初始化和现有 `pilot_random_seed17/train.json` 跑一次 forward/backward/optimizer step。检查 `context` Mask、检测、iDisp 使用同一套 96 通道适配输出。核对新 FPN 和适配层从开训起可训练，主干进入单独低学习率组。旧训练入口会默认冻结 backbone，半宽分支需显式处理新 FPN 的训练状态。
- [ ] 先跑 3–5 个 epoch 的 pilot，检查训练曲线、左右框、Mask 和视差输出。Pilot checkpoint 只用于排查。正式训练用确认过的初始化重新启动，记录种子、训练清单 SHA、实际每轮优化器步数和学习率。
- [ ] **建议的首轮正式预算为最少 30 个完整 epoch、最多 60 个。** 使用全量已冻结训练清单，每轮训练步数记为 `steps_per_epoch = len(train_loader)`，以实际成功的 optimizer step 记录累计用量。前 3 个 epoch 将检测、Mask、iDisp 和新 FPN/适配层的学习率从 `3e-5` 线性升至 `3e-4`，随后按 60 epoch 的总预算余弦降至 `3e-5`。预训练主干全程使用该学习率的 0.1 倍。保存并恢复优化器、调度器和累计步数，续训接着原曲线走。
- [ ] 每个 epoch 在冻结的 40 帧开发集上跑 R2 的线上精度。先找满足 **近车 paired recall ≥18/23，且基线命中的近车无新增漏检，一物一对 ≥17/23** 的 checkpoint。符合条件的模型按近车命中数、一物一对数、Car Mask 前景有效覆盖由高到低排序，再比较 Pred-RoI EPE 和 D1，误差越低越优先。记录每轮 Car precision 和逐目标变化。只有完成至少 30 轮、已有合格 checkpoint 且排序连续 10 轮未改善时才早停。尚无合格 checkpoint 时运行到 60 轮上限，保留最佳诊断包。独立样本留待冻结权重后复核。
- [ ] 若正式预算用完仍达不到基线，先检查后段训练和验证曲线、近车 ID 的失效路线，以及 GT-RoI 与 Pred-RoI 的差距。后段指标仍上升时记录训练不足迹象。训练集与开发集都长期停滞时，用同训练流程的 1.0× 对照核对容量假设，同时排查标注、初始化和监督差异。单项退化时按检测分数、右框、Mask 边界、iDisp 逐段定位。任何额外训练预算或阈值改动另建对照。

**每轮选模记录**　每个 epoch 填一行，近车召回、一物一对和 precision 记录分子与分母。新增漏检写数量，并关联逐目标报告中的帧 ID 和 GT ID。EPE、D1 使用同一评估口径和未四舍五入的报告值判断排序是否改善。

## 任务 4　服务器精度和速度对照

- [ ] 用同一批 40 帧、逐帧标定和完全相同的 R0/R1/R2 策略，分别运行当前 1.0× Car 前景包与 0.5× 训练包。输出四类 GT 数、TP/FP/FN、recall、precision、零对／一对／多对。对 Car 列出相对 1.0× 新增漏检的帧和实例 ID。逐对记录 `post_nms`、远距过滤、iDisp 入口与最终输出。距离无法确认的标签或预测单列。
- [ ] 缩宽后重点核对检测分数漂移、右框配对、Mask 边界和 iDisp 有效性。复用 `projected(..., foreground=True)` 将 Car 预测前景有效性回写原图，统计预测 Mask 与有效视差共同覆盖的 GT 前景有效像素占比。分别给出全部近车 GT 和共同命中 GT 的分母。将这项覆盖与普通 Pred-RoI 有效像素覆盖分列，EPE、D1 在共同 GT 与共同有效像素上对齐。空分母标 `N/A`。记录当前 Car precision **18/26** 与候选差值。
- [ ] 服务器测速重点是 **10 Hz 和 20 Hz 的 120 秒回放**。用同一张 GPU、同样的输入顺序、同步和输出字段交替对照 1.0× 与 0.5×。先跑 FP32，再把 AMP 作为独立对照。分别记录 Encoder 和整链路的 P50/P95 毫秒差，以及实际完成数、P95、超时、丢帧、积压、显存与同卡进程。5 Hz 沿用既有 47.31 ms 作回归参考，按需做短回放核对入口。共享 GPU 的实测单列。
- [ ] **基础通过条件是同一 0.5× checkpoint 和推理精度同时达到速度与精度门槛。** 服务器 10 Hz 需在 120 秒内完成 **1200/1200**，端到端 **P95 ≤100 ms**，零丢帧且窗口结束无积压，单列超时。精度需达到 **近车成对召回 ≥18/23、一物一对 ≥17/23，且无新增近车漏检**，并报告 Mask 覆盖、EPE/D1 与 precision。一物一对要求 iDisp 入口和最终输出都只有同一对合格左右框。进阶 20 Hz 对应 **2400/2400、P95 ≤50 ms**，沿用同一精度口径。冻结候选后在独立近距样本上复核，按其实际 GT 数重新列出分母和相对基线的变化。
- [ ] 精度门槛未达到时，将 0.5× 的测速结果记为实验结果。完成任务 3 的诊断后，若证据指向宽度容量不足，则分别对照 **0.75×** 或 **保留 1.0× 主干、只缩 FPN/适配内部通道**。每次只动一种结构，第一轮仍保留对外四尺度 ×96 通道，并沿用相同精度和速度口径。

## 任务 5　导出并验证板端

- [ ] `export_edge_frontend.py` 从权重解析实际编码器。旧 manifest 的 `backbone: "v2"` 仍正常加载，半宽 manifest 使用 `"v2-050"`，并核对权重 SHA、OpenStereo 提交、NCHW 与实际输出字段。显式导出选项必须匹配 checkpoint；已有 V3 速度原型维持原入口。运行时对半宽引擎复用现有在线解码与普通 paired NMS。
- [ ] 用配套的 0.5× 权重分别导出三种静态输入尺寸的 ONNX，在部署设备上构建 FP32/FP16 TensorRT 引擎，并验证引擎缺失、尺寸错误、权重或编码器标签错误，以及在线结果与 PyTorch 对齐。对比回读权重及导出前端后的原生 Mask 输出，核对 Car `context` 的有效阈值和像素掩码一致，单次阈值校准可复验。使用服务器现有 Python 3.8 环境时保持运行时兼容。
- [ ] 服务器候选通过开发集和独立样本复核后上 Orin NX。同板同功耗、同输入、同输出做 1.0× 与 0.5× 的编码器对照，记录温度、功耗、时钟和 P50/P95。板端原生 PyTorch 给参考结果，**加速 10 FPS**是部署门槛，定速 120 秒记录 1200 对的窗口内完成数、积压和超时，端到端 P95 以 100 ms 为目标。通过 10 Hz 后再测进阶 20 Hz。
- [ ] 服务器和板端各归档可复现命令、代码与权重 SHA、静态引擎 manifest、逐帧时延和精度结果。报告分别给出编码器节省的毫秒数、整条链路节省的毫秒数，以及 Car 一物一对达成情况。
